# Web3 转行学习计划（可执行版）

> 依据：《Web3转行学习清单.md》（`learning/Web3转行学习清单.md`）
> 配套提醒：工作日（周一至周五）每天 14:00 提醒进入学习状态，周末例外
> 周期：12 周（约 3 个月）；主项目：测试资产充值提现系统

## 一、总体安排

| 项目 | 说明 |
|---|---|
| 目标岗位 | Web3 后端 / 钱包平台 / 链上数据 / 支付（复用你现有的系统设计、故障处理、性能优化经验） |
| 技术栈 | Python + web3.py（或 Java + web3j，二选一）＋ Solidity（读到会测）＋ Foundry |
| 主项目 | 测试资产充值提现系统（阶段 3–5 贯穿） |
| 第一阶段岗位调研 | 第 1 周收集 15–20 个职位，圈出高频要求，锁定主方向 |

### 每日 / 每周节奏（配合 14:00 提醒）
- **按周推进**：以周为单位推进——本周只做本周清单，完成该周核心产出与验收后，才进入下一周；不赶进度、不跳周。
- **工作日 14:00–16:00**：进入学习状态，读当天主题文档 + 跑一个小实验（核心时段）
- **工作日晚间（可选）**：补读资料、复盘当日、回看卡住的点
- **周末**：留一段 2–4 小时完整时间写主项目（阶段 1–2 周末做动手实验）
- **每周日**：只记三件事——**做成了什么 / 卡在哪里 / 下周先解决什么**

> 清单上的勾，留到自己能讲清楚、动手复现时再打。每周末推进一格，第 N 周清单没勾完，不进入第 N+1 周主线。

## 三、每周执行详情

### 阶段 ①（第 1–2 周）：读懂一笔链上交易

**第 1 周｜岗位调研 + 链上概念**
- ☐ 收集 15–20 个可申请职位，记录地点、职级、语言、技能要求（第一周就看职位）
- ☐ 理解区块、交易、状态、节点各自负责什么
- ☐ 理解哈希与数字签名，弄清地址 / 私钥 / 公钥关系
- ☐ 分清钱包软件与链上资产；了解助记词、HD 钱包、托管模式
- ☐ 对比 Bitcoin UTXO 与 Ethereum 账户模型
- ☐ 理解确认、最终性与链重组

**第 2 周｜Ethereum 细节 + 第一次动手**
- ☐ 读懂交易的 from / to / value / data / Nonce / Chain ID
- ☐ 理解 Gas 用量、Gas 限额、EIP-1559 费用字段
- ☐ 分清原生币与 ERC-20，理解 decimals 与最小单位
- ☐ 弄清交易哈希、回执、日志、内部调用各能说明什么
- ☐ 动手：只用于学习的钱包，在本地链/测试网完成一笔转账，记录金额、手续费、区块号、状态；再看一笔代币转账，对比目标地址与实际收款地址
- ☐ 分清主网 / 测试网 / 本地链；了解 L2 执行与结算关系

> 验收：能解释"谁签了这笔交易、节点收到什么、为何要手续费、成功回执证明什么、何时可视为业务完成"。

---

### 阶段 ②（第 3–4 周）：用熟悉的语言接入链

**第 3 周｜RPC + 合约交互**
- ☐ 装好 web3.py（或 web3j）与 Foundry（forge / anvil / cast）
- ☐ 通过 JSON-RPC 查询区块、余额、交易、回执、事件日志
- ☐ 分清 eth_call 与发送交易（读操作 vs 状态变更）
- ☐ 理解 ABI、函数参数编码、事件 topics 与 data
- ☐ 读取 ERC-20 余额与精度，解析 Transfer 事件

**第 4 周｜Solidity 读到会测 + 部署**
- ☐ Solidity：状态变量、可见性、事件、自定义错误、权限判断
- ☐ 理解 storage / memory / calldata 与外部调用风险
- ☐ 读懂 transfer / approve / allowance / transferFrom
- ☐ 用 OpenZeppelin 部署测试代币，写成功与失败路径测试
- ☐ 认识重入、无界循环、权限错误、代理升级的基本风险
- ☐ 动手：部署测试代币，完成余额查询→授权→转账→事件解析；故意提交余额不足 / 权限不足 / 错误参数，确认能区分**业务失败**与 **RPC 故障**

> 验收：给合约地址和 ABI 能读数据、发交易、解释失败；代码重启后仍能查到原交易。

---

### 阶段 ③（第 5–6 周）：把链上数据接稳（充值模块）

**第 5 周｜扫描入账 + 一致性**
- ☐ 按区块范围扫描，支持从指定高度补扫
- ☐ 保存检查点，服务重启后能继续；扫描/入账进度可追溯
- ☐ 记录链、合约、交易、日志位置、区块哈希，设计去重约束
- ☐ 定义确认/最终性策略，明确适用哪条链
- ☐ 处理 RPC 限流、断连、日志范围限制，失败后能补回

**第 6 周｜账务与重组**
- ☐ 链上记录与内部余额**分开存**；余额变化都有账本流水；用数据库事务 + 唯一约束保证一致
- ☐ 金额用整数最小单位 / 精确十进制，禁用浮点数，不假设都是 18 位精度
- ☐ 模拟重组：被撤销的充值若已变可用余额如何回滚（写进设计）
- ☐ 测试：同范围连续扫两次不重复；中途停机重启补齐；模拟分支替换撤销失效记录；RPC 恢复后补回遗漏区间

> 验收：能演示一次中断恢复 + 一次重组处理，并解释哪些可重试、哪些必须账本调整。

---

### 阶段 ④（第 7–8 周）：管好提现和交易状态

**第 7 周｜提现状态机 + 幂等**
- ☐ 定义申请 / 冻结 / 审批 / 待发送 / 确认 / 失败的状态及转换
- ☐ 提现请求幂等标识，同一请求不重复扣款
- ☐ 同地址并发统一管理 Nonce，处理重启与 Nonce 空洞
- ☐ 区分构建交易、签名、广播、等待回执，保存追踪信息

**第 8 周｜签名边界 + 异常**
- ☐ 广播超时后查询核对原交易，避免直接生成第二笔付款
- ☐ 处理 Pending 过久与同 Nonce 替换，保留原交易与替换关系
- ☐ 区分执行失败与状态未知；资金解冻有明确依据
- ☐ 签名端与业务服务分离：业务提交受约束请求，签名端校验链 / 资产 / 地址 / 金额 / 审批条件
- ☐ 测试密钥不进仓库与日志；审批与签名有审计记录；定义限额与超限处理
- ☐ 反复问自己：链上已付款但库更新失败，重试会怎样？节点不及时返回，凭什么判断可解冻？

> 验收：用异常测试证明同一提现不会重复付款，解释每笔冻结资金最终去向，给出人工核查入口。

---

### 阶段 ⑤（第 9–12 周）：把项目做成面试材料

**第 9 周｜项目收尾 + 架构文档**
- ☐ 明确启动路径（版本、配置、测试资产来源）
- ☐ 画架构图与充值/提现状态机，说明数据与资金流转
- ☐ 实现链上与账本对账，记录差异、原因、修复过程

**第 10 周｜监控 + 测试沉淀**
- ☐ 监控扫描延迟、RPC 错误、Pending 时长、对账差异
- ☐ 保留重组、重复请求、进程中断、并发交易测试结果

**第 11 周｜演示 + 项目介绍**
- ☐ 录制 5 分钟演示：正常流程 + 一个故障恢复场景
- ☐ 写项目介绍：解决什么问题、为何拆服务、哪最容易出错、如何验证无重复入账/付款
- ☐ 留一次失败实验，说明发现与改进

**第 12 周｜简历 + 投递**
- ☐ 能解释确认/最终性、Nonce、重组、幂等、账务一致性；能设计签名边界并说清限制
- ☐ 把过去的架构取舍、线上事故、性能优化经验对应到岗位
- ☐ 准备中英文简历，能用英语介绍项目并答技术追问
- ☐ 投递前检查地点、时区、雇佣方式、语言要求；每周整理反馈，只补影响目标岗位的缺口

> 判断：能独立接入一条链、展示充值/提现/对账、回答关键异常场景，即可认真申请；后续按面试反馈展开，不必等所有公链学完。

1. **定目标**：从本周清单取今天 1–2 个勾（"今天做 X"）
2. **学材料**：读对应文档 / 官方资料对应章节（资料见第六节）

4. **留痕**：把结果、卡点记进每周追踪表；说不清的地方回到原文核对

> 14:00 提醒只负责把你"拉进学习状态"；具体学什么看本周清单当天勾选。
