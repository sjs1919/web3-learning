## ① 读懂一笔链上交易（第 1～2 周）

**基础**
- [ ] 区块 / 交易 / 状态 / 节点各自职责
- [ ] 哈希与数字签名；地址、私钥、公钥关系
- [ ] 钱包软件 vs 链上资产；助记词、HD 钱包、托管模式
- [ ] Bitcoin UTXO vs Ethereum 账户模型
- [ ] 确认、最终性、链重组（为何刚入块记录还会变）
- [ ] 主网 / 测试网 / 本地链；L2 执行与结算关系

**Ethereum 必懂**
- [ ] 交易字段 from / to / value / data / Nonce / Chain ID
- [ ] Gas 用量 / 限额 / EIP-1559 费用字段
- [ ] 原生币 vs ERC-20；最小单位与 decimals
- [ ] 交易哈希 / 回执 / 日志 / 合约内部调用各说明什么

**动手**：学习钱包在本地链/测试网转账，记录金额、手续费、区块号、执行状态；再看一笔代币转账，比较目标地址与实际收款地址。
**完成标准**：能向开发者讲清——谁签名、节点收到什么、为何要手续费、成功回执证明什么、何时算业务完成。

## ② 用熟悉语言接入链（第 3～4 周，Java→web3j）

**RPC 与合约交互**
- [ ] JSON-RPC 查区块 / 余额 / 交易 / 回执 / 事件日志
- [ ] 分清 eth_call（读）与发送交易（写）
- [ ] ABI、参数编码、事件 topics 与 data
- [ ] 读 ERC-20 余额与精度，解析 Transfer 事件
- [ ] 构建、签名、广播交易并持续追踪
- [ ] 处理超时 / 限流 / 错误响应，记录排查上下文

**Solidity（读懂+测试即可）**
- [ ] 状态变量、函数可见性、事件、自定义错误、权限
- [ ] storage / memory / calldata；外部调用风险
- [ ] 读懂 transfer / approve / allowance / transferFrom
- [ ] 用 OpenZeppelin 部署测试代币，写成功/失败路径测试
- [ ] 认识重入、无界循环、权限错误、代理升级风险

**工具＝Foundry**：Forge（构建测试）/ Anvil（本地链）/ Cast（查询调用）。
**完成标准**：给合约地址+ABI 能读数据、发交易、解释失败；重启后仍能查到原交易。

## ③ 把链上数据接稳（第 5～6 周，写充值模块）

- [ ] 按区块范围扫描，支持从指定高度补扫
- [ ] 保存检查点，重启续扫；进度可追溯
- [ ] 记录链/合约/交易/日志位置/区块哈希，建去重约束
- [ ] 重复投递不重复入账
- [ ] 定义确认/最终性策略，明确适用链
- [ ] 识别区块哈希变化，撤销失效数据并重处理有效分支
- [ ] 处理 RPC 限流/断连/日志范围限制，失败补数据
- [ ] 校验目标链、代币合约、收款地址、金额（不只看代币名）

**账务铁律**：链上记录与内部余额分开存；每次变化有账本流水；DB 事务+唯一约束保证一致；金额用整数最小单位/精确十进制，**禁浮点**，不假设都是 18 位。
**必答设计题**：被撤销充值已变成可用余额，重组时怎么处理？（不能只删扫描记录）

**必留测试**
- [ ] 同范围扫两次不重复入账
- [ ] 扫描中途停进程，重启补齐
- [ ] 模拟旧分支被替换，失效撤销、余额恢复一致
- [ ] RPC 恢复后补回遗漏区间

**完成标准**：能演示中断恢复 + 重组处理，讲清哪些可重试、哪些必须账本调整。

## ④ 管好提现与交易状态（第 7～8 周，写提现模块）

- [ ] 申请/冻结/审批/待发送/确认/失败 状态及转换条件
- [ ] 提现幂等标识，同一请求不重复扣款
- [ ] 同地址并发统一管 Nonce，处理重启与 Nonce 空洞
- [ ] 区分构建/签名/广播/等回执，保存追踪信息
- [ ] 广播超时先查原交易，不直接发第二笔
- [ ] Pending 过久与同 Nonce 替换，保留原交易与替换关系
- [ ] 区分执行失败与状态未知；解冻要有依据
- [ ] 成功后核对实际转账，完成内部账务与链上对账

**签名边界独立**：业务服务提交受约束请求，签名端校验链/资产/地址/金额/审批；本地测试密钥演示边界，生产再评估 HSM/MPC/托管（核实 KMS 是否支持所需算法编码）。
- [ ] 测试密钥不进仓库和日志；审批与签名有审计
- [ ] 单笔/累计限额、地址规则、超限处理
- [ ] 模拟并发提现、广播超时、费用过低、服务重启

**两个必答问题**：① 链上付款成功但 DB 更新失败，重试会怎样？② 节点没及时返回，凭什么判断可解冻？
**完成标准**：异常测试证明同一提现不重复付款，能解释每笔冻结资金去向；无法自动判断的给人工核查入口与证据。

## ⑤ 做成面试材料（第 9～12 周）

- [ ] 明确启动路径（版本、配置、测试资产来源）
- [ ] 画架构图 + 充值/提现状态机
- [ ] 链上与账本对账，记录差异/原因/修复
- [ ] 监控扫描延迟、RPC 错误、Pending 时长、对账差异
- [ ] 保留重组/重复请求/中断/并发测试结果
- [ ] 5 分钟演示：正常流程 + 一个故障恢复
- [ ] 一段项目介绍（问题、拆服务、易错点、如何验证不重）
- [ ] 留一次失败实验：发现了什么、怎样改
- [ ] 中英文简历，能英语介绍项目并答追问

**投递口径**：学习项目就写学习项目，不冒充生产；资深案例讲复杂系统/交付/故障责任，链上项目补领域知识。
**结项判断**：能独立接一条链 + 演示充提对账 + 答关键异常场景 → 可认真投递，不必等学完所有公链。
